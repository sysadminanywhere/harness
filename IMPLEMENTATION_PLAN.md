## Цель

Создать локальный центр управления несколькими проектами: пользователь ведёт канбан-план в Harness, а Codex работает с реальными файлами выбранного проекта и отчитывается обратно через файловый протокол.

## Целевой сценарий

Выбрать проект → создать карточку → запустить её → Harness создаёт `current-task.md` → Codex выполняет задачу → Codex записывает статус и отчёт → Harness обновляет карточку на канбане.

## Этап 1. Модель проектов

- Создать реестр проектов.
- Добавить проект по пути к папке.
- Переключаться между проектами.
- Не удалять файлы при удалении проекта из Harness.
- Проверять существование папки и показывать Git-ветку.
- Хранить отдельную доску для каждого проекта.

Критерий готовности: можно переключаться между несколькими локальными проектами и видеть разные планы.

## Этап 2. Файловый протокол проекта

В каждой папке проекта создать:

```text
.harness/
├── project.json
├── plan.json
├── current-task.md
├── status.json
├── events.jsonl
├── context.md
├── requests/
└── reports/
    └── latest.md
```

Назначение файлов:

- `plan.json` — канбан и карточки;
- `current-task.md` — активная задача для Codex;
- `status.json` — машинный статус;
- `events.jsonl` — журнал событий;
- `context.md` — общий контекст проекта;
- `requests/` — команды от Harness;
- `reports/latest.md` — последний отчёт Codex.

Критерий готовности: после перезапуска Harness состояние восстанавливается из файлов проекта.

## Этап 3. Синхронизация с Codex

При запуске карточки Harness:

1. записывает задачу в `current-task.md`;
2. создаёт команду в `.harness/requests/`;
3. переводит карточку в `В работе`;
4. отслеживает `status.json`, `events.jsonl` и `reports/`.

Codex должен:

- читать `current-task.md`;
- выполнять задачу в проекте;
- добавлять события в `events.jsonl`;
- обновлять `status.json`;
- сохранять итоговый отчёт в `reports/latest.md`.

Критерий готовности: Harness показывает, что Codex начал работу, выполняет проверки или заблокирован.

## Этап 4. Инструкция для Codex

В проекте создать или аккуратно дополнить `AGENTS.md`:

```md
## Harness protocol

If `.harness/current-task.md` exists, read it before starting work.

During work:
- append important events to `.harness/events.jsonl`;
- update `.harness/status.json`;
- do not overwrite user instructions;
- write the final report to `.harness/reports/latest.md`.
```

Нельзя перезаписывать существующий `AGENTS.md`. Необходимо:

- определить наличие Harness-блока;
- добавить его только при отсутствии;
- создать резервную копию перед изменением;
- поддержать ручное отключение интеграции.

## Этап 5. Канбан и контроль

Для карточки добавить:

- проект;
- исполнителя;
- статус;
- приоритет;
- критерии готовности;
- зависимости;
- изменённые файлы;
- последний отчёт;
- историю событий;
- флаг `requiresApproval`.

Статусы:

```text
Идеи → Готово → В работе → Ожидает решения → Проверка → Завершено
                                      └──────→ Заблокировано
```

Команды:

- запустить;
- поставить на паузу;
- отменить;
- повторить;
- вернуть в работу;
- подтвердить результат;
- запросить отчёт.

Критерий готовности: пользователь всегда понимает, что делает Codex и почему карточка находится в текущем статусе.

## Этап 6. Локальный планировщик

После появления файлового протокола добавить встроенный планировщик без сетевых вызовов и API-ключей.

Локальный планировщик используется для:

- декомпозиции большой цели;
- предложения карточек;
- определения зависимостей;
- анализа отчётов Codex;
- предложения следующего шага;
- обнаружения блокировок.

Планировщик возвращает структурированный JSON. Он не меняет файлы проекта напрямую: Harness проверяет и применяет только разрешённые изменения состояния.

## Этап 7. Надёжность и безопасность

- атомарная запись через временный файл и переименование;
- восстановление после повреждённого JSON;
- защита от одновременных записей;
- журнал всех изменений;
- отсутствие внешних AI API и сетевых вызовов;
- подтверждение опасных действий;
- запрет выхода за пределы выбранной папки;
- корректная работа путей Windows;
- обработка ручных изменений файлов.

## Очередность реализации

1. Реестр проектов.
2. Выбор папки проекта.
3. Создание `.harness`.
4. Чтение и запись `plan.json`.
5. Генерация `current-task.md`.
6. Чтение `status.json`.
7. Чтение `events.jsonl`.
8. Отображение отчёта Codex.
9. Интеграция с `AGENTS.md`.
10. Контрольные точки и подтверждения.
11. Локальный планировщик.
12. Автоматическое предложение следующего шага.

## Первый вертикальный срез

Выбрать проект → создать карточку → запустить её → получить `current-task.md` → выполнить задачу в Codex → увидеть отчёт и новый статус на канбане.

## Проверки готовности

- `npm run check` проходит.
- Проект можно добавить и выбрать после перезапуска.
- `.harness` создаётся только внутри выбранной папки.
- Ручное изменение `status.json` отражается на доске.
- Отчёт Codex отображается в карточке.
- Повторный запуск не создаёт дубликаты событий.
- Существующий `AGENTS.md` не теряет пользовательские инструкции.
- Основной сценарий проверен в браузере на Windows.
