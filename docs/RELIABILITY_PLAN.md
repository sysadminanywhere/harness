# Harness Lab — план надёжного исполнения

Дата: 2026-10-25. Основной сценарий реализован и проверен. Актуальные исправления и доказательства: [WORKFLOW_CORRECTIONS.md](WORKFLOW_CORRECTIONS.md) и [IMPLEMENTATION_AUDIT.md](IMPLEMENTATION_AUDIT.md). Ниже сохранён исходный план требований; исторические флажки не заменяют текущую матрицу проверки.

## Цель и границы

Довести основной сценарий до надёжной работы: выбрать проект → запустить задачу → получить результат конкретного запуска → проверить его → подтвердить завершение → передать следующую задачу.

Основание — проверка реализации от 2026-10-25: три ошибки P1 и две ошибки P2. Прохождение существующего `npm test` не закрывает эти проблемы: нужны регрессионные сценарии ниже. Исторические отметки в IMPLEMENTATION_PLAN.md и ROADMAP.md не являются подтверждением готовности этих сценариев.

Сохраняем локальное хранение и файловый протокол `.harness`, без обязательных AI API. Автоматический запуск внешнего Codex-процесса и интеллектуальная декомпозиция целей — отдельные направления после исправления надёжности.

| --- | --- | --- | --- |
| 1. Изоляция сохранений | P1 | — | План и ответы API остаются в своём проекте |
| 2. Модель запусков и результатов | P1 | 1 | Завершение задачи сохраняется до запуска следующей |

## 1. Изоляция сохранений между проектами

- [ ] Фиксировать projectId и контекст загруженной доски при создании операции сохранения.
- [ ] Разделить очереди сохранения по проектам; отправлять каждую операцию по сохранённому projectId.
- [ ] Сериализовать изменения внутри проекта с актуальной revision; не отправлять несколько снимков со старой revision после успешного предыдущего сохранения.
- [ ] Применять ответ только к тому проекту и контексту загрузки, которому он принадлежит. Поздний ответ A не должен заменять доску B, в том числе при переключении A → B → A.
- [ ] Аналогично защитить поздние ответы loadBoard и syncProject. Конфликт revision показывать без молчаливой потери несохранённых правок.

Файлы: `board.js`, при необходимости `project.js` и отдельный модуль состояния.

Приёмка: задержать запрос A, переключиться на B и сохранить B; проверить URL, содержимое обоих plan.json и текущую доску. Повторить с обратным порядком ответов, быстрыми последовательными изменениями и конфликтом из второго окна.

## 2. Постоянные запуски и результаты

- [ ] Ввести уникальный runId для каждой попытки исполнения; taskId остаётся идентификатором карточки.
- [ ] Хранить записи запусков и отчёты по runId, например `.harness/runs/<runId>/run.json` и `report.md`: projectId/taskId, исполнитель, время, статус, результаты проверок и ссылка на отчёт.
- [ ] Разделить состояния исполнителя и карточки: успешное исполнение переводит карточку в review, а пользовательское подтверждение — в done.
- [ ] До dispatch следующей задачи сохранять результат завершённого запуска и обновлять его карточку на сервере. Операция должна повторяться без дубликатов после рестарта.
- [ ] Установить порядок записей и восстановление после сбоя между сохранением результата, обновлением плана и запуском следующей задачи.
- [ ] Учитывать revision при серверном обновлении плана: ручные правки не теряются, устаревшие клиенты получают конфликт и могут обновиться.
- [ ] Возвращать сохранённые результаты через API независимо от текущего status.taskId; UI должен подхватывать новые ревизии плана.
- [ ] Сохранить current-task.md, status.json и reports/latest.md как совместимый мост. Для старого исполнителя без runId фиксировать только наблюдаемый результат текущего запуска до его замены; не приписывать неизвестный старый отчёт новой задаче.

Файлы: `server.js`, `board.js`, `scripts/smoke.mjs`, новые модули по необходимости.

Приёмка: A завершилась, B запустилась до очередного опроса браузера — A всё равно в review со своим отчётом. Повторить без открытого браузера, с включённым worker, после рестарта и после сбоя между записями. Повторное чтение файлов не создаёт повторные результаты.

## 3. Адресное управление исполнением

- [ ] Проверять projectId/taskId/runId и допустимость перехода для pause, resume, cancel, retry и return.
- [ ] Возвращать 409 для устаревшей команды без изменения активного запуска; неизвестные задачи отклонять.
- [ ] Отделить отмену элемента очереди от отмены активного исполнения. Повторный запуск создаёт новый runId и сохраняет предыдущий результат.
- [ ] Привязать claim и heartbeat к запуску и владельцу; проверять владение при переходах. Истёкшая аренда и её освобождение должны иметь явную семантику.
- [ ] Проверить оба пути запуска — файловый мост и локальную команду: ни один не должен перезаписывать занятого исполнителя.

Приёмка: пока работает B, отправить pause/cancel/resume для старого запуска A. B и его current-task.md не меняются. Повторить старую команду после retry той же карточки, а также конкурентный запуск двумя исполнителями.

## 4. Полный контракт очереди

- [ ] Передавать с доски priority, dueDate, executionMode и остальные необходимые поля задания; сервер валидирует и нормализует их один раз.
- [ ] Обрабатывать queued=true в UI: задача отображается ожидающей, а не уже выполняющейся. Показывать реального активного исполнителя.
- [ ] Сохранить правило сортировки: приоритет → ближайший дедлайн → порядок постановки, включая стабильный порядок при одинаковых временных метках.
- [ ] Исключить дублирование одной ожидающей попытки при повторном клике или повторе запроса.
- [ ] Применять политику проекта и подтверждения к автоматическому запуску через любой путь, включая файлового исполнителя.

Приёмка: создать high-карточку с дедлайном через UI при занятом исполнителе. Проверить её поля в queue.json и фактический выбор worker. Дополнительно проверить повторный клик, паузу активной задачи и запрет автономного старта в manual-профиле.

## 5. Завершение по результату конкретного запуска

- [ ] Определить контракт результата: taskId/runId, отчёт, перечень обязательных проверок с исходами и подтверждение критериев.
- [ ] Сохранять критерии и список обязательных проверок в контексте запуска; обновлять их только явно, с записью в аудит.
- [ ] Проверять завершение на сервере: отчёт принадлежит этому запуску, обязательные проверки успешны, критерии подтверждены, переход допустим.
- [ ] Разделить отчёт исполнителя и приёмку человеком. Для ручных критериев записывать решение пользователя; это не заменяет результат обязательной автоматической проверки.
- [ ] Отклонять отчёт другой задачи, старого retry или шаблон latest.md. Показывать конкретную причину отказа в UI.
- [ ] Сохранять отчёты предыдущих попыток и показывать отчёт выбранной карточки/запуска.

Приёмка: complete без отчёта, с отчётом другой задачи, старой попытки, failed-проверкой или неподтверждённым критерием отклоняется прямым API-запросом. Успешный запуск принимается, сохраняет автора приёмки и переводит карточку в done.

## 6. Сквозная приёмка и описание продукта

- [ ] Включить регрессионные тесты этапов 1–5 в воспроизводимые проверки. Дополнить существующие API-тесты проверками реального UI, а не поиском строк в исходниках.
- [ ] Выполнить `npm test`, целевые сценарии Playwright и `git diff --check` в изолированных папках.
- [ ] Пройти сценарий с двумя проектами, двумя последовательными задачами, worker, закрытием браузера, рестартом сервера и повторным запуском неудачной задачи.
- [ ] Проверить чтение существующего `.harness` без потери плана, инструкций и истории. Перед миграцией создавать резервную копию; документировать восстановление.
- [ ] Обновить README, IMPLEMENTATION_PLAN.md и ROADMAP.md по фактически прошедшей приёмке. Указать: файловая передача задания внешнему исполнителю, шаблонный planner, демонстрационный Execution.
- [ ] Для изменений состава файлов обновить desktop/PWA packaging и проверить, что новые модули включены в архивы. Проверить запуск собранного Windows-приложения перед релизом.

## Правило выполнения

Каждый этап — отдельный проверяемый срез: воспроизведение ошибки → исправление → регрессионная проверка → обновление отчёта и Git staging. Отмечать пункт выполненным только после соответствующей приёмки. При провале обязательной проверки этап остаётся незавершённым.

План не включает публикацию релиза, перенос тега или запуск внешнего AI-исполнителя. Эти действия требуют отдельного задания.
