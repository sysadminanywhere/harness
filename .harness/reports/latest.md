# Проверка идеи и реализации Harness Lab — 2026-10-25

Проверка завершена. Исходный код не изменялся. Найдены ошибки в центральном сценарии управления несколькими проектами и исполнением задач.

## Оценка идеи

Локальная доска с единым файловым контрактом для Codex, IDE, скрипта и человека — понятное ядро продукта. Контекст остаётся в проекте, API-ключи для самого Harness не нужны, отчёт и история доступны вне UI. Уже работают хранение планов, реестр проектов, локальные команды, версии и файловый мост.

Запуск Codex сейчас записывает задание и статус в файлы. Автоматического запуска внешнего Codex-процесса нет. Встроенный planner возвращает три шаблонных шага, а вкладка Execution содержит демонстрацию. Эти границы нужно учитывать при оценке готовности продукта.

## Найденные проблемы

1. **P1 — сохранение может попасть в другой проект** (`board.js:57`). Payload снимается сразу, а projectId читается позднее внутри Promise-очереди. Ответ также безусловно заменяет текущий boardState.data. Воспроизведено выполнением исходной saveBoard в Node VM с управляемым переключением: payload проекта A отправлен на `/api/projects/project-b/plan`, после ответа на доске B лежат карточки A. Нужна фиксация projectId на момент операции и проверка принадлежности ответа перед обновлением UI.

2. **P1 — очередь теряет завершение предыдущей задачи** (`server.js:157-172`, `board.js:144`). Сервер хранит одно текущее состояние и запускает следующую задачу, а UI узнаёт завершение только из последнего status.taskId. Воспроизведено: завершить A, передать B через queue/next до очередного syncProject; A остаётся working. Включённый worker может создать такую последовательность без ручного действия. Нужны постоянные результаты запусков по taskId/runId и серверное обновление карточки до dispatch.

3. **P1 — управление старой карточкой заменяет активную задачу** (`server.js:173-180`). controlTask не проверяет соответствие taskId текущему запуску. Воспроизведено: после запуска B отправлена pause для A; HTTP 201, status.taskId стал A, статус paused. Нужны проверка активного запуска и разделение команд очереди/активного исполнителя.

4. **P2 — доска теряет приоритет и дедлайн при постановке в очередь** (`board.js:116`). runCard отправляет taskId/title/description/criteria/executor, но не priority/dueDate. Воспроизведено: high-карточка с dueDate=2026-10-26 попала в очередь как priority=medium, dueDate=null. Серверный тест сортировки отправляет поля напрямую, поэтому не замечает ошибку UI.

5. **P2 — критерии завершения не связаны с конкретным результатом** (`board.js:121-122`, `server.js:173-180`). UI проверяет наличие общего reports/latest.md и непустого массива criteria. Не проверяются выполнение критериев, принадлежность отчёта задаче и результаты обязательных проверок. Сервер принимает complete без отчёта (подтверждено HTTP 201 в изолированном проекте). Нужен отчёт конкретного запуска и серверная проверка завершения.
